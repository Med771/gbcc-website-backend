# Функционал GBCC Website Backend — простое подробное описание

Документ для тех, кому нужно **понять, что умеет сервис**, без углубления в каждую строку кода. Точные поля запросов и ответов смотрите в **Swagger UI** (`/swagger-ui.html`) или OpenAPI (`/v3/api-docs`). Технический паспорт: [PROJECT_PASSPORT.md](PROJECT_PASSPORT.md).

---

## Что это за приложение

Это **backend сайта GBCC** на Java и Spring Boot. Он отдаёт **REST API** (по умолчанию порт **8080**, префикса `/api` нет). Данные хранятся в **PostgreSQL**, схема обновляется миграциями **Flyway**. Файлы по умолчанию складываются в **локальную папку** на диске (путь из настроек `app.file.bucket`).

Пользователи делятся на роли: **OWNER** (полный контроль), **ADMIN** (управление контентом, заявками, CRM в своей зоне ответственности), **CUSTOMER** (покупатель: заказы, профиль, реферальная программа). Вход по **JWT**, токены отдаются в **HttpOnly-cookie** (access и refresh), чтобы браузер мог работать с сессией безопаснее, чем при хранении токена в `localStorage`.

---

## Вход, выход и сессия (`/auth`)

- **Логин** — проверка логина и пароля, выдача пары cookie: короткоживущий access-токен и долгоживущий refresh-токен.
- **Обновление сессии** — по refresh-cookie выдаётся новая пара токенов, чтобы пользователь не разлогинивался слишком часто.
- **Выход** — инвалидация refresh-токена на сервере и сброс cookie.

Без валидного access-токена (или без специальных «гостевых» правил ниже) многие операции просто недоступны: Spring Security проверяет cookie, а часть правил **дополнительно** проверяется внутри сервисов (роль, владелец записи, назначенный менеджер и т.д.).

---

## Аккаунты (`/account`)

- **Регистрация покупателя** — создание учётной записи с ролью CUSTOMER (публичный сценарий для сайта).
- **Создание администратора** — отдельный сценарий для выдачи роли ADMIN (по политике безопасности доступен не всем подряд — см. конфигурацию и Swagger).
- **Профиль «я»** — просмотр и изменение данных текущего пользователя.
- **Работа с покупателями для админов** — активация, правка данных, удаление; отдельные операции только для не-OWNER аккаунтов, чтобы случайно не «уронить» владельца системы.
- **CRM-поля покупателя** — привязка к организации CRM и менеджеру-привлечёнцу (`PATCH /account/customer/{id}`).
- **Аналитика покупателя** — ручные показатели и автоподсчёт по доставленным заказам (`GET/PUT /account/customer/{id}/analytics`).
- **Карточка сотрудника** — профиль ADMIN/OWNER: должность, соцсеть, реквизиты, display ID (`GET/PUT /account/{id}/staff-profile`).
- **Список и карточка аккаунта** — для администрирования пользователей.
- **Блокировка / разблокировка** — временное отключение входа для аккаунта.

При старте приложения может автоматически создаваться **учётная запись OWNER** из настроек (если её ещё нет) — это «корневой» администратор.

## Каталог товаров (`/product`)

Сервис отвечает за **витрину**: классы/серии товаров, карточки, поиск, похожие товары, скидки, популярность, расширенный контент страницы товара. Справочник **типов (модификаций) удалён** — уникальность товара по классу, серии, марке и габаритам.

- **Публичное чтение** — список, фильтры, карточка, группированный поиск, похожие позиции — чтобы сайт мог показывать каталог без авторизации. В ответе витрины: `originalPrice`, `finalPrice`, при нулевой цене — `priceLabel` «Договорная».
- **Создание и изменение** — для администраторов: полное создание, замена данных, частичное обновление (patch), управление **фотографиями** товара (загрузка и удаление по связи с файлом), поле **остатка** `stockQuantity`.
- **Склад** — `GET /product/stock` (список остатков с фильтрами) и `PATCH /product/{id}/stock` (ручная корректировка) — только ADMIN/OWNER.

Таксономия **типа товара (`product_type`)** удалена (миграция V030): фильтрация по серии и классу, без `typeIds` / `typeName`.

---

## Файлы (`/file`)

- **Загрузка файла** — multipart-запрос, файл сохраняется в хранилище, в ответе — метаданные и ключ для дальнейшего использования (например, фото товара).
- **Список и скачивание** — получение списка загруженных объектов и выдача содержимого по ключу.
- **Удаление** — удаление файла из хранилища (с учётом прав доступа).

---

## Новости (`/news`)

- **Публичное чтение** — список новостей, карточка, справочник **категорий**.
- **Редакция** — создание, полная замена, частичное обновление — для ролей с правами на контент (как правило ADMIN/OWNER; точные правила — в Security и сервисе).

---

## Акции / промо (`/promotion`)

- **Просмотр** — одна акция или список с параметрами поиска (часть сценариев доступна без входа — для отображения на сайте).
- **Управление** — создание, обновление, частичное изменение, удаление — для администраторов.

---

## Заказы витрины B2C (`/order`)

- **Оформление заказа** — покупатель создаёт заказ из корзины; проверяется **остаток** на складе.
- **История и детали** — список своих заказов и просмотр конкретного заказа; у менеджеров — фильтр по **CRM-организации**.
- **Смена статуса** — обработка заказа с записью истории; при **DELIVERED** начисляются реферальная и менеджерская комиссии (если применимо).
- **Правка менеджером** — **PATCH `/order/{id}`**: контакты, адрес, комментарий, доставка, привязка к CRM-организации (до финальных статусов).

В заказе: контактные поля, **deliveryFee**, **netTotal**, опциональная связь с **`crm_organization`**.

---

## Поддержка и чаты (`/support/conversations`)

- **Создание обращения** — пользователь (или гость) заводит **диалог поддержки**.
- **Переписка** — добавление сообщений в диалог.
- **Статусы** — смена состояния диалога (открыт, закрыт и т.п. — по бизнес-логике).
- **Списки** — «мои» диалоги для авторизованного пользователя; общий список и детали — для сотрудников поддержки.

**Гость без аккаунта** после создания обращения получает секретный токен; дальнейший доступ к **этому** диалогу возможен по заголовку **`X-Support-Token`**, чтобы не требовать регистрации у человека, который просто написал в поддержку.

---

## Заявка с сайта «связаться с нами» (`/contact-requests`)

- **Отправка заявки** — публично: любой посетитель оставляет контакт и текст.
- **Очередь для админов** — список и карточка заявки.
- **Взять / отпустить** — менеджер **закрепляет** заявку за собой или **освобождает**, чтобы другой мог взять. Так распределяется нагрузка между администраторами.

---

## Заявка на сотрудничество (`/cooperation-requests`)

Логика **аналогична контактным заявкам**: публичная отправка, просмотр списка и карточки для staff, взятие и освобождение заявки ответственным.

---

## Реферальная программа (`/referral`)

- **Учёт кликов** — публичная точка: фиксация перехода по реферальной ссылке (для аналитики и начислений).
- **Личный кабинет реферера** — профиль программы «для меня»: код, приглашённые, запрос на вывод средств, обновление своего invite-кода где это разрешено правилами.
- **Админка рефералов** — просмотр кликов, комиссий, регистраций, очереди выводов; **выплата** или **отклонение** заявки на вывод.

Параметры программы задаются в конфигурации: **7%** комиссии за первый доставленный заказ приглашённого клиента, **2%** за последующие (`app.referral.commission-percent-new-client` / `commission-percent-returning-client`), минимальная сумма вывода, база ссылок.

Отдельно: **комиссия менеджера-привлечельца** за заказы клиентов, которых он привёл в CRM (**`manager_referral_commission`**), список — **GET `/crm/manager-commissions`** (ADMIN/OWNER).

## Модуль CRM (`/crm/**`)

CRM — это **отдельный контур** для B2B: организации, лиды, задачи, взаимодействия, поставки, контракты, карта и сводные цифры. Доступ только у **ADMIN и OWNER**; **OWNER** видит всё, **ADMIN** — в основном то, что **назначено** ему (организации, лиды, задачи как исполнитель и т.д.), а записи **без назначения** — по правилам только у OWNER. Детали скоупа реализованы в политике доступа CRM.

### Организации (`/crm/organizations`)

Юридические или деловые **контрагенты**: создание, редактирование, поиск с пагинацией, карточка. Поле **ИНН**. У организации есть **контакты** (люди) с **должностью** и **соцсетями** (JSON), **филиалы** (отдельные адреса): CRUD под `/crm/organizations/{id}/branches`. При изменении контакта ведётся **история изменений**. **Переназначение ответственного** — только **OWNER**.

### Лиды (`/crm/leads`)

**Потенциальные клиенты** до оформления как организация: создание, обновление, поиск, карточка. **Конвертация лида в организацию** — отдельная операция: лид «превращается» в полноценную карточку организации. Переназначение ответственного — снова сценарий для OWNER.

### Задачи (`/crm/tasks`)

Напоминания и работы по организации или лиду: создание, обновление, удаление, поиск с фильтрами (организация, лид, статус, исполнитель, сроки), просмотр одной задачи. Отдельный список **просроченных открытых** задач в рамках доступного пользователю скоупа.

### Взаимодействия (`/crm/interactions`)

Журнал **звонков, встреч, писем и т.д.**: кто, когда, с кем, результат, **тип взаимодействия** (`interactionType`). Создание, изменение, удаление, поиск с фильтрами по организации, лиду, автору, датам, типу и фрагменту текста результата.

### Поставки B2B (`/crm/supplies`)

Поставки, привязанные к **организациям CRM** (не путать с заказами витрины): создание, изменение, удаление, поиск по организации и периоду, просмотр карточки. **Календарь** — `GET /crm/supplies/calendar` (`from`/`to`); в карточке — время, адрес, объект, филиал, товар каталога.

### Контракты (`/crm/contracts`)

Договор с организацией: создание, изменение, удаление, поиск, карточка. У контракта есть **строки графика** (этапы/объёмы/даты — по полям DTO): список, добавление, правка, удаление строки.

### Карта (`/crm/map`)

- **Точки на карте** — агрегированные данные для отображения: организации с координатами, поставки с адресом доставки, **объекты компании**.
- **Объекты компании** — собственные точки/объекты GBCC на карте: список, создание, обновление, удаление.

### Метрики (`/crm/metrics`)

**Сводка** по CRM в рамках прав текущего пользователя — для дашборда (количественные показатели считаются в сервисе метрик).

## Ошибки и единый формат ответа

При сбоях валидации или бизнес-правил сервер отдаёт структурированное тело **`ApiErrorResponse`**: время, HTTP-статус, тип ошибки, сообщение, путь запроса, при необходимости — **список полей** с текстами ошибок по каждому полю формы. Обработчик сосредоточен в `GlobalExceptionHandler`.

## Документация API и тесты

- **Swagger UI** — интерактивная документация и «песочница» для запросов.
- **Тесты** — unit и WebMvc-тесты всегда; интеграционные с реальной PostgreSQL в Docker — отдельным профилем Maven (см. README и паспорт проекта).

## Деплой

В репозитории может быть workflow GitHub Actions: по push в `main` или вручную выполняется **SSH на сервер** и команда **docker compose** для пересборки и запуска backend. Секреты (хост, ключ, путь) хранятся в настройках репозитория GitHub.
